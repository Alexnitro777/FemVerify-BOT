# Способ вступления — план фиксов (`inviteTracker.ts`)

Рабочая заметка для будущей правки. Баг: поле «Способ вступления» в анкете либо не определяется («Неизвестно»), либо иногда определяется неправильно (чужой пригласивший).

## Корень проблемы

Детект построен на **диффе счётчиков `uses`**: бот держит снапшот `Map<code, {uses, inviterId}>`, а на `guildMemberAdd` заново тянет инвайты и ищет тот, у которого `uses` вырос относительно снапшота. Подход опирается на два хрупких допущения:

1. между снапшотами произошёл **ровно один** релевантный джойн;
2. к моменту детекта снапшот ещё **актуален** (использованный инвайт ещё «виден»).

Оба ломаются на одноразовых инвайтах и на всплесках входов.

## Первичная проверка (до любого кода)

Есть ли у бота право **«Управление сервером»**. Без него `guild.invites.fetch()` всегда падает (`inviteTracker.ts:72-76`) → способ входа «Неизвестно» **всегда**. В логах будет предупреждение `не удалось получить инвайты`. Если симптом «не определяется никогда» — почти наверняка это, и код тут ни при чём.

---

## Фикс A — одноразовые инвайты (главная причина «иногда не определяется»)

При использовании одноразового инвайта Discord шлёт `INVITE_DELETE` и `GUILD_MEMBER_ADD`, **порядок не гарантирован**. Оба идут через `runExclusive` (сериализуются), но если первым выполнится `inviteDelete` (`:143-149`), он выкинет код из `state.invites`, и ветка «пропавших» в `detectJoinMethod` (`:90-97`) уже ничего не найдёт. Гонка ~50/50 → отсюда «иногда».

**Решение — не терять удалённый инвайт, а буферизовать:**

```
recentlyDeleted: Map<code, { inviterId, deletedAt }>

on inviteDelete (внутри runExclusive):
   entry = state.invites.get(code)
   if entry: recentlyDeleted.set(code, { inviterId: entry.inviterId, deletedAt: now })
   state.invites.delete(code)
```

`detectJoinMethod` собирает кандидатов из **трёх** источников, склеивая по `code`:
- инвайты во `fresh`, у которых `uses > prev.uses`;
- коды из снапшота, которых нет во `fresh` (delete обработался **после** join);
- коды из `recentlyDeleted` в окне ~10 сек (delete обработался **до** join).

Закрывает обе очерёдности гонки. `recentlyDeleted` чистить по таймстампу (окно короткое), иначе вручную удалённый админом инвайт припишется следующему вошедшему.

## Фикс B — неправильная атрибуция при всплесках (главная причина «неправильно»)

Сейчас код берёт **первый** инвайт с выросшим `uses` и делает `break` (`:80-87`). При нескольких выросших счётчиках (массовый заход, лаг, пропущенные события) припишется первый по порядку итерации — случайный.

**Решение — собирать всех кандидатов и не угадывать:**

```
candidates = (выросшие во fresh) ∪ (пропавшие) ∪ (recentlyDeleted), dedupe by code

candidates.length === 1 → это пригласивший
candidates.length === 0 → проверка vanity → UNKNOWN
candidates.length  >  1 → UNKNOWN (неоднозначно) + лог кодов
```

Убирает «неправильно»: при двусмысленности честно пишем «Неизвестно» вместо чужого пригласившего. Полностью одновременные джойны диффом не разделить в принципе — лучше «Неизвестно».

## Фикс C — пустой/устаревший базовый снапшот

Сценарии «Неизвестно»:
- инвайт создан, пока бот был офлайн (пропущен `inviteCreate`) → `prev === undefined`, условие `uses > prev.uses` ложно (`:83`);
- человек зашёл раньше, чем `cacheGuildInvites` добежал до его сервера в стартовом цикле (`:120-124`);
- пропущенное gateway-событие.

**Решение:**
- в детекте обрабатывать `prev === undefined && uses > 0` как **слабый кандидат** (код впервые увиден уже с использованиями) — учитывать только если других кандидатов нет;
- периодический ре-кэш снапшота (раз в N минут) — самовосстановление после пропущенных событий.

---

## Фикс D — vanity и «пропало больше одного»

- **vanity**: `vanityUses` инициализируется в `cacheGuildInvites` (`:63`), после чистого старта работает. Дыра только если `fetchVanityData()` упал на старте (нет vanity/уровня буста) → `prevVanity` остаётся `null`, первое использование не ловится (`:110`). Достаточно залогировать, багом не считать.
- **`missing.length === 1`** (`:94`): если параллельно истёк/удалён ещё один инвайт — единственного «пропавшего» нет. Объединение источников (Фикс A) + правило «>1 ⇒ Unknown» (Фикс B) это покрывают.

---

## Фикс E — диагностика

Логировать в `detectJoinMethod`: размер снапшота до/после, список выросших кодов, содержимое `recentlyDeleted`, итоговое число кандидатов. Тогда причина (нет прав / гонка / всплеск) видна на проде сразу.

---

## Приоритет

1. **Проверка права «Управление сервером»** — первым делом.
2. **A + B** — основной выигрыш (одноразовые инвайты + неверная атрибуция).
3. **C / E** — устойчивость и наблюдаемость.

## Границы (останутся как есть)

Полностью одновременные входы по разным инвайтам diff-метод не различает — лимит подхода, не баг. Правильное поведение для бота-верификатора здесь — «Неизвестно» (Фикс B).

## Объём правки

Всё помещается в `inviteTracker.ts`, внутри существующего `runExclusive`. Без изменения схемы БД и сигнатур (`saveJoinMethod`/`getJoinMethod`/`Application.joinMethod` не трогаем).
