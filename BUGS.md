## Что проверено

Просмотрены все файлы `src/`, схемы и запросы БД, конфигурация Docker и сборки, документация сценариев. `npm ci --ignore-scripts --no-audit --no-fund` и `npm run build` завершились успешно на Node.js `24.16.0`. Тестового фреймворка и линтера в проекте нет.

Для существенных находок выполнены изолированные проверки собранного кода с подменой БД и Discord API. Поведение кэша ролей, разрешений каналов и событий удаления также проверялось на установленном `discord.js`. В частности, воспроизведены повторная выдача ЧСП при возврате ролей, перезапись финального статуса обновлением канала, выдача verified поверх ЧСП, обработка чужого типа апелляции при глобальном снятии ЧСП и обрезание текста апелляции.

Рабочие Discord и MySQL не использовались; Docker в окружении проверки отсутствует. Для ошибок конкурентности указана последовательность операций, при которой они возникают. Это перечень найденных дефектов, а не гарантия отсутствия других ошибок. На момент исходного аудита код не исправлялся; последующие изменения отражены в FIX_REPORT.md.

## P1 — высокий приоритет

### B001. Обработанная ошибка ловушки всё равно завершает процесс бота

- **Где:** `src/trapChannel.ts:42–62`; аналогичная конструкция в `src/roleTag.ts:104–110`.
- **Условие:** операция внутри блокировки возвращает отклонённый Promise, например из-за недоступной БД при обработке сообщения ловушки.
- **Ошибка:** `void next.finally(...)` создаёт отдельный отклонённый Promise без обработчика. Внешний `.catch()` обрабатывает только исходный `next`.
- **Последствие:** Node.js с настройками проекта аварийно завершает весь процесс. Локальная проверка на Node 24 подтвердила завершение с кодом 1 даже после обработки исходной ошибки.
- **Исправление:** обработать Promise, возвращённый `finally`, либо выполнять очистку через `next.then(cleanup, cleanup)`.

### B002. Возврат ролей после амнистии способен повторно выдать ЧСП

- **Где:** `src/roles.ts:36–45`; вызовы после удаления роли в `src/modals/unchspReason.ts:81–94`, `src/buttons/appealReview.ts:287–305`, `src/sync.ts:197–203`.
- **Условие:** у участника есть сохранённые роли для возврата, а Gateway ещё не обновил кэш после удаления ЧСП.
- **Ошибка:** одиночный `member.roles.remove(roleId)` в discord.js возвращает новый объект участника. Код игнорирует его и вызывает `roles.add(array)` на прежнем объекте; библиотека собирает полный набор ролей из старого кэша, включая ЧСП.
- **Последствие:** бот возвращает ЧСП сразу после его снятия, хотя запись уже амнистирована. Изолированный запуск реального менеджера discord.js дал итоговый набор `[restored, guild, blacklist]`.
- **Исправление:** использовать актуальный возвращённый объект либо один согласованный набор ролей, явно исключающий снимаемую блокировку.

### B003. Амнистия ЧСЗ/ЧСА изменяет анкету и возвращает роли, снятые из-за ЧСП

- **Где:** `src/buttons/appealReview.ts:277–305`; `src/storage.ts:673–677`.
- **Условие:** удовлетворяется апелляция на ЧСЗ или ЧСА, а у пользователя есть запись в `applications`.
- **Ошибка:** `amnestyApplication` и восстановление `application.removedRoles` выполняются для любого типа апелляции. Разделения по типу перед этими действиями нет.
- **Последствие:** `approved`, `pending` или действующий `blacklisted` превращаются в `amnestied`. При одновременном ЧСП возвращаются снятые им роли, исчезают запись о действующем ЧСП и основание для его автоматической защиты.
- **Исправление:** изменять анкету и возвращать снимок ролей ЧСП только при амнистии ЧСП. Специальные списки обрабатывать независимо.

### B004. Обновление одного поля может отменить уже принятое решение модератора

- **Где:** `src/storage.ts:691–699`, `351–383`; аналогично `954–995` для апелляций. Один из вызывающих путей — `src/questionRestore.ts:36–46`.
- **Условие:** обновление канала читает строку `pending`, затем другой обработчик принимает/отклоняет/блокирует заявку, после чего первое обновление сохраняет прочитанную строку.
- **Ошибка:** `updateApplication` выполняет чтение, объединение с patch и сохранение всей записи; `updateAppeal` тоже записывает все прочитанные поля.
- **Последствие:** финальный статус, reviewer и другие изменения перезаписываются устаревшими значениями. Изолированная проверка: модератор установил `approved`, обновление только `questionChannelId` вернуло `pending` и обнулило reviewer.
- **Исправление:** обновлять только переданные поля одним UPDATE; переходы статусов выполнять условно через `claim*`/сравнение версии записи.

### B005. Верификация не учитывает ЧСП в БД, если Discord-роль отсутствует

- **Где:** `src/buttons/verifyStart.ts:20–45`, `src/modals/verifySubmit.ts:34–53`, `src/storage.ts:388–416`.
- **Условие:** запись уже `blacklisted`, но роль ЧСП не выдалась, временно отсутствует либо блокировка появилась между проверкой роли и резервированием анкеты.
- **Ошибка:** вход и submit проверяют преимущественно Discord-роли; из статусов анкеты запрещён только `pending`. `reserveApplication` также запрещает только `pending` и допускает замену `blacklisted`.
- **Последствие:** новая анкета перезаписывает ЧСП, его причину и `removedRoles`; защита больше не считает пользователя заблокированным. Изолированная проверка подтвердила открытие формы при `applications.status='blacklisted'` и отсутствующей роли.
- **Исправление:** проверять приоритет глобального ЧСП и повторять проверку допустимого перехода внутри транзакции резервирования.

### B006. Глобальная верификация выдаёт verified поверх ЧСП и допускает перезапись блокировки

- **Где:** `src/sync.ts:224–259`.
- **Условие:** при распространении верификации на другом сервере у пользователя есть ЧСП либо ЧСП назначается параллельно с синхронизацией.
- **Ошибка:** роль verified добавляется без проверки блокировки. Ранее прочитанный `pending` изменяется через безусловный `updateApplication`, без атомарного захвата.
- **Последствие:** заблокированный участник получает роль доступа. При конкурирующих решениях `blacklisted` может быть затёрт значением `approved`. Проверка настоящей функции с подменой API подтвердила добавление verified при наличии и роли ЧСП, и статуса `blacklisted`.
- **Исправление:** сделать ЧСП приоритетным, использовать атомарный переход и согласовать операции одного пользователя между серверами.

### B007. Два способа выдачи ЧСП не распространяют его на остальные серверы

- **Где:** `src/modals/reviewReason.ts:29–58`, `src/modals/verifySubmit.ts:56–115`.
- **Условие:** ЧСП выдан кнопкой рассмотрения анкеты либо автоматически за возраст менее 13 лет.
- **Ошибка:** оба пути меняют только локальные роли и БД; `applyGlobalBlacklist` не вызывается. В отличие от них, прямая команда делает это в `src/modals/chspReason.ts:93`.
- **Последствие:** участник, уже находящийся на других серверах проекта, сохраняет там доступ до отдельной синхронизации или нового входа. При блокировке на вторичном сервере основной также может не выдать роль, необходимую для подачи апелляции.
- **Исправление:** вызывать общий механизм глобального ЧСП после успешного локального решения во всех путях выдачи.

### B008. Уборщик считает любой старый текстовый канал категории своим и удаляет его

- **Где:** `src/questionCleanup.ts:76–105`.
- **Условие:** в `questionCategoryId` находится обычный текстовый канал, например инструкция, старше 48 часов, не связанный с текущими анкетами/апелляциями.
- **Ошибка:** `sweepCategoryOrphans` проверяет категорию, возраст и отсутствие связи; происхождение канала не проверяется.
- **Последствие:** посторонний канал безвозвратно удаляется как осиротевший вопрос. Изолированное исполнение обработчика подтвердило удаление обычного канала `rules`.
- **Исправление:** удалять только каналы с записью о создании ботом или устойчивой собственной меткой; одного нахождения в категории недостаточно.

### B009. Формы модерации не проверяют права повторно при отправке

- **Где:** `src/modals/reviewReason.ts:21–40`, `src/modals/chspReason.ts:15–45`, `src/modals/unchspReason.ts:14–44`, `src/modals/specialBlacklistReason.ts:23–66`; общий маршрутизатор `src/handlers/interactionCreate.ts:51–57`.
- **Условие:** модератор открыл форму, после чего у него отозвали нужную staff/ststaff-роль.
- **Ошибка:** проверка доступа остаётся только на исходной кнопке/команде. Маршрутизатор форм проверяет конфигурацию сервера, а сами формы не проверяют уровень доступа. Проверка иерархии цели в части форм не заменяет проверку staff/ststaff.
- **Последствие:** отправка уже открытой формы выполняет действие после отзыва полномочий. Изолированная проверка `reviewReason` без staff-ролей всё равно вызвала `claimApplication`.
- **Исправление:** проверять актуальный уровень доступа в каждом submit-обработчике до любых изменений.

## P2 — средний приоритет

### B010. Вопрос по повторной апелляции не создаётся и меняет историю обращений

- **Где:** `src/storage.ts:883–893`, вызов `src/buttons/appealReview.ts:113–129`.
- **Условие:** у пользователя уже есть историческая апелляция с `questionChannelId=NULL` и появилась новая, также без канала.
- **Ошибка:** UPDATE адресуется по пользователю и старому каналу, без `id`, типа и `pending`. Он записывает placeholder нескольким строкам, но функция считает успехом только `affectedRows===1`.
- **Последствие:** канал не создаётся, изменённые строки остаются с `pending:...`; история и параллельные типы обращения смешиваются. При двух подходящих строках изолированный вызов вернул `false` после UPDATE.
- **Исправление:** резервировать канал конкретной pending-апелляции по её `id`.

### B011. Закрытие вопроса апелляции очищает другую запись и теряет тип кнопок

- **Где:** `src/questionRestore.ts:44–51`; выбор строки в `src/storage.ts:960–995`.
- **Условие:** у участника несколько апелляций, закрывается вопрос не самого нового обращения.
- **Ошибка:** найденная по каналу апелляция обновляется только по `(guildId,userId)`, поэтому выбирается последняя запись. Восстановление кнопок вызывает `buildAppealReviewButtons(appeal.userId)` без типа.
- **Последствие:** у другого обращения теряется связь с каналом; кнопки исходной карточки затем могут обработать последнюю pending-апелляцию другого типа.
- **Исправление:** переносить точный `appeal.id` через обновление и customId; сохранять тип при восстановлении интерфейса.

### B012. При выходе участника часть апелляций и их каналов остаётся необработанной

- **Где:** `src/leaveCleanup.ts:68–80`, `src/storage.ts:896–905`, `1065–1081`.
- **Условие:** есть несколько pending-апелляций разных типов либо самая новая уже закрыта, а более старая остаётся pending.
- **Ошибка:** обработчик получает только последнюю апелляцию. `markAppealLeft` меняет все pending-записи, но возвращает `false`, если изменено больше одной.
- **Последствие:** либо pending остаётся без изменения, либо статусы становятся `left`, но карточки и каналы не закрываются. Сохранившиеся апелляционные каналы исключены из обычной TTL-очистки.
- **Исправление:** получить все pending-апелляции и атомарно завершить каждую по `id` с обработкой её карточки и канала.

### B013. Снятие ЧСП ошибочно удовлетворяет апелляцию на ЧСЗ/ЧСА

- **Где:** `src/sync.ts:164–189`, `src/modals/unchspReason.ts:74–76`.
- **Условие:** при снятии ЧСП последняя pending-апелляция пользователя относится к специальному списку.
- **Ошибка:** `getAppeal`/`claimAppeal` вызываются без ограничения типом ЧСП.
- **Последствие:** апелляция на ЧСЗ/ЧСА получает `amnestied` и закрытую карточку, но соответствующие роль и запись `special_blacklists` остаются. Более старые pending-апелляции могут вообще не обрабатываться.
- **Исправление:** при снятии ЧСП выбирать только его pending-апелляции и изменять их по точным ID.

### B014. Глобальная амнистия изменяет даже одобренные и ожидающие анкеты

- **Где:** `src/sync.ts:164–173`, `src/storage.ts:673–677`.
- **Условие:** ЧСП снимается на одном сервере, а на другом существует анкета пользователя со статусом `approved` или `pending`.
- **Ошибка:** `amnestyApplication` вызывается для любой существующей анкеты; SQL не ограничен `status='blacklisted'`.
- **Последствие:** ранее одобренная анкета перестаёт быть источником глобальной верификации; pending исчезает из очереди без обычной обработки её карточки и вопроса. Изолированная проверка подтвердила переход `approved → amnestied` на другом сервере.
- **Исправление:** амнистировать только действительно заблокированные записи; другие состояния обрабатывать отдельно и условно.

### B015. Снимок снятых ролей уничтожается до успешного восстановления

- **Где:** `src/storage.ts:673–677`; вызовы в `src/modals/unchspReason.ts:74–94`, `src/buttons/appealReview.ts:278–305`, `src/sync.ts:172–203`.
- **Условие:** возврат ролей не удался из-за API/иерархии либо участник отсутствует на одном из серверов.
- **Ошибка:** `amnestyApplication` сначала обнуляет `removedRoles`; Discord-операция выполняется позже или пропускается.
- **Последствие:** бот теряет сведения о ролях, которые ещё нужно вернуть. Исправление разрешений или повторный вход уже не помогают восстановить их автоматически.
- **Исправление:** хранить невосстановленные роли до подтверждённого возврата и предусмотреть повтор операции.

### B016. Уже снятая специальная блокировка возвращается из снимка ролей ЧСП

- **Где:** `src/roles.ts:12–18`, `36–45`; снятие специального списка — `src/modals/specialBlacklistReason.ts:160–176`.
- **Условие:** роль ЧСЗ/ЧСА попала в `removedRoles` при выдаче ЧСП, затем специальную блокировку сняли, а позже сняли ЧСП.
- **Ошибка:** восстановление добавляет сохранённую роль ЧСЗ/ЧСА без проверки актуальной записи в `special_blacklists`.
- **Последствие:** участник снова получает уже отменённую блокировку; база и Discord расходятся.
- **Исправление:** восстанавливать специальные blacklist-роли по текущим данным БД либо удалять их из всех снимков при отмене соответствующей блокировки.

### B017. Команды снятия ЧС отказывают при наличии записи только в БД

- **Где:** `src/commands/unchsp.ts:54–59`, `src/specialBlacklistHelper.ts:81–86`.
- **Условие:** участник присутствует, запись о блокировке есть, но Discord-роль отсутствует, например после неудачной выдачи.
- **Ошибка:** команда завершается по отсутствию роли ещё до открытия формы. При этом submit-обработчики умеют учитывать запись БД: `src/modals/unchspReason.ts:52–57`, `src/modals/specialBlacklistReason.ts:161–166`.
- **Последствие:** штатной командой нельзя отменить такую блокировку; защита продолжает считать её действующей и может вернуть роль позднее.
- **Исправление:** разрешать снятие при наличии роли или соответствующей записи в БД; одинаково проверять состояние в команде и submit.

### B018. Вопрос может создаться после финального решения

- **Где:** `src/storage.ts:446–456`, `883–893`; обработчики вопросов в `src/buttons/review.ts` и `src/buttons/appealReview.ts`.
- **Условие:** кнопка прочитала `pending`, другой обработчик завершил заявку, после чего выполняется резервирование вопроса.
- **Ошибка:** UPDATE для `questionChannelId` не проверяет `status='pending'`. После решения поле уже NULL и подходит под сравнение.
- **Последствие:** создаётся новый приватный канал для завершённой заявки после того, как финальный обработчик уже выполнил очистку.
- **Исправление:** проверять pending в обоих этапах резервирования и адресовать конкретное обращение.

### B019. Старая форма или подтверждение обрабатывает новое обращение того же пользователя

- **Где:** `src/buttons/review.ts:55`, `331–332`, `src/modals/reviewReason.ts:34–40`, `src/buttons/appealReview.ts:248–255`, `380–381`.
- **Условие:** модератор открыл форму/подтверждение для обращения №1; оно было закрыто другим действием; пользователь успел подать №2; модератор отправляет прежнюю форму.
- **Ошибка:** customId и атомарный захват определяют обращение только по пользователю и иногда типу, без номера/ID исходной заявки.
- **Последствие:** решение по старому обращению применяется к новой pending-записи. Изолированная проверка подтвердила отклонение анкеты №2 старой формой для №1.
- **Исправление:** включать ID/версию обращения в компоненты и проверять её при захвате записи.

### B020. Повторная апелляция имеет одновременно два разных срока ожидания

- **Где:** `src/buttons/appealStart.ts:19`, `87–93`; `src/modals/appealSubmit.ts:11`, `70–78`; `src/buttons/appealReview.ts:35`, `313–316`; `src/commands/appeal.ts:67`.
- **Ошибка:** стартовая кнопка и информационная карточка используют неделю, submit и ЛС об отказе — 48 часов.
- **Последствие:** обещанная в ЛС дата не совпадает с фактической доступностью формы. Результат зависит от сохранённого пути через выбор типа. Проверка отказа трёхдневной давности подтвердила блокировку стартовой кнопкой.
- **Исправление:** определить одно правило и вынести его в общий источник для всех проверок и текстов.

### B021. Лимит двух апелляций не проверяется при сохранении

- **Где:** проверка только в `src/buttons/appealStart.ts:74–78`; отсутствует в `src/buttons/appealSelectType.ts:28–43`, `src/modals/appealSubmit.ts:62–81`, `src/storage.ts:836–869`.
- **Условие:** ранее полученная кнопка выбора типа остаётся доступной после двух завершённых обращений.
- **Ошибка:** submit и транзакция резервирования проверяют pending, но не установленный лимит истории.
- **Последствие:** можно сохранить третью и последующие апелляции вопреки объявленному правилу.
- **Исправление:** проверять количество в транзакции создания, одинаково во всех путях входа.

### B022. Submit апелляции проверяет любую блокировку вместо выбранного типа

- **Где:** `src/modals/appealSubmit.ts:51–60`; выбор типа — `src/buttons/appealSelectType.ts:28–43`.
- **Условие:** открыта форма ЧСЗ, затем ЧСЗ сняли, но ЧСА или ЧСП остался.
- **Ошибка:** submit требует хотя бы одну blacklist-роль, не проверяя соответствие `type`.
- **Последствие:** сохраняется апелляция на уже отсутствующую блокировку; модераторы рассматривают неверное состояние. Изолированный запуск подтвердил сохранение ЧСЗ-апелляции при единственной роли ЧСА.
- **Исправление:** проверять конкретный тип и его действующее состояние непосредственно перед резервированием.

### B023. Бот не получает доступ к созданному им приватному вопросу

- **Где:** `src/buttons/review.ts:191–213`, `src/buttons/appealReview.ts:144–166`.
- **Условие:** бот имеет Manage Channels/Manage Roles, но не Administrator и не одну из staff-ролей.
- **Ошибка:** ViewChannel запрещается everyone и разрешается только заявителю и staff/ststaff. Отдельного разрешения боту нет.
- **Последствие:** канал создаётся, но бот не может отправить вопрос и прочитать переписку для архива. Проверка расчёта разрешений реальными классами discord.js подтвердила отсутствие ViewChannel у бота.
- **Исправление:** явно включать в перезаписи ID бота с необходимыми разрешениями просмотра, отправки и чтения истории.

### B024. Карточка ловушки не восстанавливается после удаления

- **Где:** `src/index.ts:49–52`; подписки `src/trapChannel.ts:324–332`.
- **Ошибка:** кэш сообщений отключён через `MessageManager: 0`, а `Partials.Message` не включён. discord.js не генерирует события удаления для неизвестных кэшу сообщений.
- **Последствие:** обработчики одиночного и массового удаления не восстанавливают предупреждение ловушки. Оно возвращается только по другому событию, например после перезапуска или срабатывания ловушки.
- **Исправление:** включить message partials или обрабатывать соответствующие raw-события. Изолированная проверка установленной discord.js подтвердила отсутствие ожидаемых событий при пустом кэше.

### B025. Неудачное удаление вопроса всё равно очищает связь с каналом

- **Где:** `src/questionCleanup.ts:56–69`, `92–106`; `src/questionRestore.ts:34–46`.
- **Условие:** Discord отказал в удалении канала или API временно недоступен.
- **Ошибка:** `restoreReviewButton` вызывается независимо от результата `deleteQuestionChannel`.
- **Последствие:** живой приватный канал теряет связь с обращением; интерфейс может предлагать новый вопрос, а дальнейшая очистка и логирование работают с неполными данными.
- **Исправление:** очищать ссылку и восстанавливать кнопку только после успешного удаления или подтверждённого отсутствия канала.

### B026. Обычный member-update может ошибочно снять роль за тег

- **Где:** `src/roleTag.ts:45–54`, `190–200`.
- **Условие:** Gateway-пакет содержит пользователя без необязательного поля `primary_guild`, при этом пользователь продолжает носить тег.
- **Ошибка:** отсутствие поля трактуется как отсутствие тега, хотя discord.js в этой ситуации сохраняет прежнее значение пользователя.
- **Последствие:** бот снимает корректную роль за тег при постороннем обновлении участника. Изолированная проверка raw-обработчика подтвердила вызов удаления роли на пакете с `user: { id }`.
- **Исправление:** отличать отсутствующее поле от явного `null`; при отсутствии использовать известное состояние или запрашивать его повторно.

### B027. Автоматическая верификация сообщает успех, когда роль не выдана

- **Где:** `src/buttons/verifyStart.ts:45–57`; похожий неверный подсчёт в `src/commands/sync_all.ts:53–58`.
- **Условие:** выдача verified завершается ошибкой API/иерархии.
- **Ошибка:** ошибка `roles.add` подавляется, после чего отправляются успешный лог и ответ; массовая синхронизация также увеличивает счётчик успехов.
- **Последствие:** участнику сообщают о верификации, но доступ не появляется; административные логи и итог синхронизации вводят в заблуждение. Изолированная проверка с Missing Permissions подтвердила успешный ответ и успешный лог.
- **Исправление:** учитывать результат Discord-операции, сообщать об ошибке и не увеличивать успешные счётчики при отказе.

### B028. До половины разрешённого текста апелляции скрыто от модератора

- **Где:** `src/questions.ts:60–68`, `src/ui.ts:95–100`, `src/modals/appealSubmit.ts:116–125`.
- **Ошибка:** форма принимает до 2000 символов, но единственная карточка рассмотрения содержит только первые 1000 и многоточие. Интерфейса чтения оставшегося текста из БД нет.
- **Последствие:** модератор принимает решение по неполному обращению; ключевое объяснение в конце ему недоступно. Проверка апелляции длиной 1020 символов подтвердила отсутствие её последних 20 символов в карточке.
- **Исправление:** показывать полный принятый текст, разделяя его между полями/сообщениями или прикладывая файл.

### B029. Импорт ролей обнуляет канал pending-анкеты без завершения её интерфейса

- **Где:** `src/commands/import_roles.ts:138–169`; `src/storage.ts:545–549`, `573–577`.
- **Условие:** у участника есть pending-анкета с вопросом, роль verified или ЧСП назначена вне обычного решения, затем запускается `/внести`.
- **Ошибка:** импорт использует upsert, меняющий статус и обнуляющий `questionChannelId`, но не закрывает канал и не обновляет карточку прежнего обращения.
- **Последствие:** вопрос теряет связь с анкетой, старая карточка сохраняет активные элементы, обычная обработка завершения и архивирование обходятся.
- **Исправление:** перед импортом учитывать текущую pending-запись и проводить её через общий путь завершения с очисткой связанных объектов.

### B030. Канал с перепиской удаляется даже при неудачном сохранении архива

- **Где:** `src/channels.ts:15–24`, `81–95`; `src/ui.ts:586–615`.
- **Условие:** получение сообщений, отправка транскрипта или доступ к каналу логов завершаются ошибкой, хотя дальнейшее удаление исходного канала доступно.
- **Ошибка:** чтение истории может вернуть неполный набор; `postQuestionLogMessage` поглощает ошибку и ничего не возвращает. `deleteQuestionChannel` в любом случае продолжает удаление.
- **Последствие:** бот безвозвратно удаляет единственный экземпляр переписки без обещанного архива либо с неполным архивом.
- **Исправление:** возвращать явный результат сохранения; при включённом архивировании не удалять исходный канал до подтверждения доставки транскрипта или сохранять его в надёжную очередь повторной отправки.

## P3 — низкий приоритет

### B031. Транскрипт содержит только последние 500 сообщений

- **Где:** `src/channels.ts:15–24`; обещание полного транскрипта — `docs/features.md:127–129`.
- **Ошибка:** чтение истории прекращается при `messages.length >= 500`; более ранняя переписка не загружается.
- **Последствие:** у длинного вопроса начало обсуждения безвозвратно теряется после удаления канала, хотя архив выглядит как завершённый транскрипт.
- **Исправление:** архивировать всю историю порциями либо явно обозначать ограничение и сохранять оставшуюся часть отдельно.

### B032. Инструкция предлагает restart для применения новых переменных окружения

- **Где:** `README.md:216`, `220`; `CLAUDE.md:33`; аналогичное правило в `.antigravity/rules/femverify.md`.
- **Ошибка:** `docker compose restart` перезапускает существующий контейнер с прежним окружением и не применяет изменения `environment` в compose-файле.
- **Последствие:** новые DB_HOST/DB_PASSWORD и другие env не вступают в силу, хотя оператор выполнил указанную инструкцию.
- **Исправление:** для изменений env указывать пересоздание через `docker compose up -d` с необходимым пересозданием контейнера; restart оставить для перечитывания конфигурации из БД. Также учитывать, что сохранённые значения `app_config` имеют приоритет над env.

### B033. Вход по vanity-ссылке не определяется, если нет обычных инвайтов

- **Где:** `src/inviteTracker.ts:149–154`, проверка vanity находится ниже в `226–238`.
- **Условие:** сервер использует vanity-ссылку, а снимок обычных приглашений пуст.
- **Ошибка:** функция возвращает «Неизвестно» до проверки счётчика vanity.
- **Последствие:** такие вступления постоянно фиксируются как неизвестные, даже когда vanity-данные доступны. Изолированная проверка подтвердила, что `fetchVanityData` не вызывается.
- **Исправление:** проверять vanity до раннего выхода по пустому снимку обычных инвайтов.
