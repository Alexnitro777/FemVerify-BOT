# Отчёт о багах — FemVerify-BOT

Дата анализа: 2026-06-02. Версия discord.js по lock-файлу: **14.26.4**.

Ниже — баги, найденные при ревью. Для каждого: где, в чём проблема, как чинить.
Расположение указано по файлу и символу/ветке (номера строк ориентировочные —
они сдвигаются после удаления комментариев).

Текущий статус: баги 1, 2, 4, 5, 6 — исправлены; баг 3 оставлен намеренно
(ожидаемое поведение). Оба замечания подчищены.

Отдельно проверено и **багом НЕ является**: `client.once('clientReady', ...)` в
`src/index.ts`. В discord.js 14.26 строковое событие `clientReady` валидно
(старое `ready` лишь помечено deprecated), обработчик и стартовая синхронизация
ролей отрабатывают штатно.

## Баг 1 — Повреждённый текст (mojibake) в ответе модератору

- **Статус:** ✅ исправлено.
- **Severity:** низкая (косметика, но виден модераторам).
- **Файл:** `src/buttons/review.ts`, ветка `approve`, ответ при неудачном claim
  (ориентировочно строка 155).
- **Сейчас:**
  ```
  content: `Заявка уже обработана (${fresh?.status ?? 'не ��айдена'}).`,
  ```
  Литерал содержит битые байты `не ��айдена` вместо `не найдена`.
- **Проявление:** при гонке двух модераторов, если заявка уже обработана и при
  этом не находится, модератор видит сообщение с «кракозябрами».
- **Решение:** заменить на `'не найдена'`. Для сравнения — в
  `src/buttons/appealReview.ts` и `src/modals/reviewReason.ts` та же строка
  написана корректно.

## Баг 2 — Сбой выдачи роли ЧС не обрабатывается (рассинхрон статуса и роли)

- **Статус:** ✅ исправлено (результат `roles.add` проверяется, модератор получает предупреждение об иерархии ролей).
- **Severity:** средняя/высокая (нарушает основную защитную логику).
- **Файл:** `src/modals/reviewReason.ts`, ветка `action === 'blacklist'`:
  ```
  await member?.roles.add(config.roles.blacklist).catch(() => null);
  ```
- **Проблема:** статус заявки уже атомарно переведён в `blacklisted`
  (`claimApplication` выше по коду). Если сама выдача роли ЧС упала (роль бота
  ниже роли ЧС в иерархии, нет права ManageRoles и т.п.) — ошибка молча
  проглатывается. В итоге: в БД статус `blacklisted`, пользователю ушло ЛС «вы в
  чёрном списке», но **роли ЧС у него фактически нет**. А вход в верификацию
  (`src/buttons/verifyStart.ts`) блокируется именно по наличию роли
  `config.roles.blacklist` — значит такой пользователь спокойно пройдёт
  верификацию заново.
- **Контраст:** в `src/buttons/review.ts` (ветка approve) выдача роли проверяется,
  и при сбое статус откатывается в `pending` с предупреждением модератору.
- **Решение:** проверять результат `roles.add` (`.then(() => true).catch(...)`),
  и при неудаче предупреждать модератора (followUp с текстом про иерархию ролей),
  по аналогии с approve. Опционально — откатывать статус или явно сообщать, что
  роль ЧС не была выдана.

## Баг 3 — Видимость slash-команд не совпадает с ролевым доступом из конфига

- **Статус:** оставлено намеренно — ожидаемое поведение (роли из конфига должны иметь соответствующие Discord-права).
- **Severity:** средняя (конфиг-«грабли»: модераторы могут не видеть команды).
- **Файлы:** `src/commands/forms.ts`, `formsbl.ts`, `tag.ts`
  (`.setDefaultMemberPermissions(PermissionFlagsBits.ManageNicknames)`),
  `verify.ts`, `appeal.ts` (`...Administrator`).
- **Проблема:** `setDefaultMemberPermissions` задаёт, кому Discord по умолчанию
  **показывает** команду. Но доступ внутри бота проверяется независимо —
  `hasCommandAccess` по ролям `config.roles.mod` / `config.roles.admin`
  (`src/handlers/interactionCreate.ts`, `src/permissions.ts`). Если у модератора
  есть роль из `config.roles.mod`, но нет Discord-права `ManageNicknames`,
  команда ему просто не отображается, и серверная проверка доступа никогда не
  отрабатывает — модератор не может вызвать `/формы`, `/формычсп`, `/тег`,
  хотя по логике бота доступ у него есть.
- **Решение:** не ограничивать видимость через `setDefaultMemberPermissions`
  (не задавать её или задать `null`) и полагаться на проверку доступа в коде;
  либо явно задокументировать, что роли из конфига обязаны иметь
  соответствующие Discord-права.

## Баг 4 — Не очищается questionChannelId после отклонения/ЧС

- **Статус:** ✅ исправлено (после удаления канала вызывается `updateApplication(userId, { questionChannelId: undefined })`).
- **Severity:** низкая (несогласованность данных, без заметных последствий).
- **Файл:** `src/modals/reviewReason.ts`, блок удаления приватного канала-вопроса
  (в конце обработчика).
- **Проблема:** канал-вопрос удаляется, но `questionChannelId` в БД не
  сбрасывается. В `src/buttons/review.ts` (approve) после удаления вызывается
  `updateApplication(userId, { questionChannelId: undefined })`, здесь — нет.
  В записи остаётся ссылка на уже удалённый канал.
- **Решение:** после удаления канала вызвать
  `updateApplication(userId, { questionChannelId: undefined })`.

## Баг 5 — reviewReason ищет сообщение заявки не в том канале

- **Статус:** ✅ исправлено (channelId и messageId берутся из `app.reviewMessageUrl`).
- **Severity:** низкая/средняя (проявляется при смене канала в конфиге).
- **Файл:** `src/modals/reviewReason.ts`, обновление исходного сообщения заявки:
  `messageId` берётся из `app.reviewMessageUrl`, но `messages.fetch` выполняется
  в `config.channels.review`.
- **Проблема:** если канал ревью в конфиге сменили после создания заявки,
  оригинальное сообщение лежит в старом канале, а поиск идёт в новом → сообщение
  не находится и не обновляется (остаётся с активными кнопками после решения).
  Для той же задачи `src/leaveCleanup.ts` парсит канал прямо из URL
  (`parseMessageUrl`) — это надёжнее.
- **Решение:** извлекать и channelId, и messageId из `app.reviewMessageUrl`
  (как в `parseMessageUrl`) и фетчить сообщение из этого канала.

## Баг 6 — Graceful shutdown не дожидается закрытия Discord-клиента

- **Статус:** ✅ исправлено (`shutdown` стала async, `await client.destroy()` перед `process.exit(0)`).
- **Severity:** низкая.
- **Файл:** `src/index.ts`, функция `shutdown`.
- **Проблема:** `client.destroy()` возвращает Promise, но он не ожидается —
  сразу вызывается `process.exit(0)`. Процесс может завершиться до того, как
  соединение с Discord корректно закроется.
- **Решение:** сделать `shutdown` асинхронной и `await client.destroy()` перед
  `process.exit(0)`; `closeDb()` вызывать в том же порядке.
